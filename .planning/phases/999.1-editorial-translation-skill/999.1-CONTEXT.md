# Phase 999.1: editorial-translation — Context

**Gathered:** 2026-03-23
**Status:** Ready for planning

<domain>
## Phase Boundary

Build an `editorial-translation` skill that translates a finished nonfiction document into a target language while preserving intent, readability, and formatting. Primary language pair is Spanish ↔ English, but the skill must work for any language pair. The skill is purely a production step — it does not diagnose; it delivers a translated document.

</domain>

<decisions>
## Implementation Decisions

### Execution engine
- **D-01:** Codex (OpenAI Codex CLI via the `codex` skill) is **opt-in**, not the default. Claude translates by default.
- **D-02:** Codex option requires the `codex` skill to be installed. If not installed, or if the codex call fails, fall back to Claude and notify the user.
- **D-03:** When codex is selected, it handles **both** the analysis pass and the translation — not just the translation step. The full workflow runs through codex.
- **D-04:** Codex model for translation: `gpt-5.4-mini` at `medium` reasoning effort. This is the latest OpenAI mini model; the codex skill will be updated to reflect current model options. Medium effort (not low) is used because nonfiction prose translation requires voice preservation and idiomatic accuracy.

### Two-phase convention
- **D-05:** This skill does **not** follow the diagnostic-first two-phase pattern used by editorial-structural/development/line/copy/proof. Translation is a production step, not a diagnostic. Parallel: `editorial-typesetting`, which also produces output directly.
- **D-06:** No Phase 1 diagnostic, no issue log written to `.agents/editorial-context.md`. The skill produces the translated document as its deliverable.

### Modes
- **D-07:** Single mode only — no quick/normal/refined split. The skill is quality-focused by design, appropriate for nonfiction books and articles. One thorough workflow.

### Workflow position
- **D-08:** Translation is an **optional** step that runs after `editorial-copy` (stage 4) and before `editorial-typesetting` (stage 5). Not all documents go through translation — it is a branch, not a required stage.
- **D-09:** The workflow position section in SKILL.md should show it as optional, not renumber the existing 6 stages.

### Language defaults
- **D-10:** Default target language is Spanish (`es`), not Chinese. Source language is auto-detected if not specified.
- **D-11:** Skill must work for any language pair — Spanish is the default, not a hard constraint.

### Content chunking
- **D-12:** Long documents are chunked for translation (inherited from baoyu-translate rationale: context limits). Chunk threshold and max words are configurable settings.
- **D-13:** Temp files for chunked content go in `.tmp/` in the working directory, not stdin/stdout — this is what makes codex integration practical for large chunks.

### Claude's Discretion
- Exact audience and style option set (can follow baoyu-translate's tables, adapted for Spanish as primary)
- EXTEND.md or equivalent preferences file — location and schema
- Whether to support a glossary feature (term consistency across chunks)
- Specific output directory naming convention
- Whether to include a translator's notes feature

</decisions>

<specifics>
## Specific Ideas

- baoyu-translate's audience presets (general / technical / academic / business) and style presets (storytelling / formal / technical / literal / academic / business / humorous / conversational / elegant) are good — keep them, drop the Chinese-specific examples
- baoyu-translate's `--from`, `--to`, `--audience`, `--style`, `--glossary` CLI flags are worth preserving
- The chunk threshold (default 4000 words) and chunk max words (default 5000) from baoyu-translate are reasonable starting points for this skill too
- The analysis step from baoyu-translate's refined-workflow.md (terminology extraction, tone assessment, figurative language mapping, comprehension challenges) should be preserved — it's what makes the translation editorially sound

</specifics>
